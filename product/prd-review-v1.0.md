## 二、各角色评审详情

### 🏗️ 安德（高级架构师）

> *"架构服务于业务，这份 PRD 的架构关键决策点基本空白。"*

#### 发现 1：数据链路过于理想化（严重）

PRD 2.1 节的数据链路 `AI 语义解析 → 元数据匹配 → SQL/配置生成` 是紧耦合设计。

**问题**：AI 直接生成 SQL 在医疗场景下是高风险行为——模型可能产生幻觉，生成了语义正确但逻辑错误的查询。

**建议**：引入三层架构：

```
用户输入 → 语义网关（NL → 意图 JSON）
        → 元数据中心（维度/指标匹配）
        → 参数化查询模板（非自由 SQL）
        → 数据查询层
```

AI 的输出应该是结构化的「意图 JSON」，例如：
```json
{
  "metric": "antibiotic_usage_rate",
  "dimensions": ["dept", "doctor"],
  "time_range": "2025Q1",
  "compare": "MoM"
}
```
后端用参数化模板拼接 SQL——这是医疗系统的正确做法。

**决策点**：语义网关是否独立微服务？建议独立部署，便于模型升级和 Prompt 迭代。

#### 发现 2：3 秒 SLA 缺少硬件前提说明（严重）

PRD 4.1 要求 AI 语义解析 ≤ 3 秒，但未说明模型推理的硬件条件。

| 推理方式 | 7B 模型首次延迟 | 能否达 3 秒？ |
|----------|----------------|-------------|
| CPU 推理（无 GPU） | 5-15 秒 | ❌ 不可能 |
| GPU T4 | 2-5 秒 | ⚠️ 需优化 |
| GPU A10 / RTX 3090+ | 0.5-2 秒 | ✅ 可以 |
| vLLM + Continuous Batching | 0.3-1 秒（并发时） | ✅ 可以 |

**建议**：补充硬件最低要求——至少一张 T4 GPU，推荐 A10。且需要 POC 验证 5 条典型医疗查询的端到端延迟。

#### 发现 3：并发能力缺失（中等）

7B 模型单卡并发通常 ≤ 10 个用户。如果是全院使用，高峰期可能几十个临床医生同时查询。

**建议**：补充并发指标——至少支持 20 并发 AI 对话请求。如果单卡达不到，需要设计请求队列 + 排队提示。

#### 发现 4：行级安全实现路径模糊（中等）

PRD 3.3.1 "强制注入 ORG_ID" 听起来简单，但多层下钻时容易遗漏过滤条件。

**建议**：应用层中间件方式——权限引擎解析用户角色 → 动态生成 WHERE 子句 → 注入每条 SQL。配合 Redis 缓存权限映射（30 分钟 TTL）。

### 🗄️ 安迪（DBA 专家）

> *"数据安全是红线。AI 直接生成 SQL？这需要三层防线。"*

#### 发现 1：AI 生成 SQL 的安全漏洞（严重）

PRD 没有定义 AI 生成 SQL 的约束机制。AI 模型可能生成：
- `DROP TABLE` / `TRUNCATE`
- `SELECT * FROM patients`（返回全部患者数据）
- JOIN 了不应该关联的表

**建议**：三层防线模型：

| 层级 | 机制 | 实现方式 |
|------|------|----------|
| L1 应用层 | 意图 JSON → 参数化模板，禁止自由 SQL | 元数据中心维护 SQL 模板 |
| L2 中间件层 | SQL 解析器拦截高危操作 | sqlparse + AST 白名单 |
| L3 数据库层 | 只读账号 + 查询超时 5s + 最大返回 10000 行 | PostgreSQL 资源组 / MySQL MAX_EXECUTION_TIME |

#### 发现 2：下钻 2 秒响应的数据方案（严重）

PRD 要求下钻 ≤ 2 秒。如果数据量百万级以上且多表 JOIN，实时查询基本达不到。

**建议**：
- **预聚合（Pre-aggregation）是必须的**——按院区/科室/月做物化视图，小时级刷新
- 推荐 **ClickHouse** 做分析层（列存 + 向量化执行），业务库只保留 OLTP
- 如果是 PostgreSQL 栈，用 `MATERIALIZED VIEW` + `pg_cron` 定时刷新

#### 发现 3：审计日志存储方案缺失（中等）

PRD 4.2 要求"记录所有 AI 指令"，但没说存哪里、存多久。

**建议**：
- 存储引擎：ClickHouse（列存 + 高压缩比，适合日志）
- 保留周期：在线 90 天 + 归档 3 年（医疗合规）
- 敏感字段脱敏：写入前替换患者 ID 为哈希值

#### 发现 4：数据模型 ER 图缺失（中等）

PRD 提到了维度、指标、报表，但没有定义它们之间的数据关系。

**建议补充 ER 图**，核心实体：
- `dimensions(id, name, db_field, display_name, ai_aliases, parent_id, org_id)`
- `metrics(id, name, category, sql_template, version, status, org_id)`
- `metric_dimension_bindings(metric_id, dimension_id, is_required)`
- `reports(id, name, config_json, owner_id, visibility, org_id, created_at)`
- `audit_logs(id, user_id, org_id, action, ai_prompt, sql_generated, timestamp)`

### 💻 阿德（全栈开发）

> *"PRD 功能描述够了，但缺少前端架构和数据结构约定。"*

#### 发现 1：前端架构选型空白（严重）

PRD 没有定义前端技术栈和关键架构决策：
- 报表渲染引擎：ECharts、AntV、还是自研 Canvas？
- AI 对话流式输出的方案：SSE 还是 WebSocket？内网环境下 WebSocket 有无代理兼容问题？
- 预览沙盒的数据量：前端一次加载多少数据点？超过 10000 条怎么办？

**建议**：
- 图表引擎：**Apache ECharts**（医疗行业常用，支持下钻交互、目标值标记线）
- AI 对话：**SSE（Server-Sent Events）** 优于 WebSocket（内网代理兼容性好，单向推送足够）
- 大数据量：前端做数据采样（`lodash.sampleSize`），超过 5000 点走后端聚合

#### 发现 2：意图确认的 UI 组件需求（中等）

PRD 3.1.1 "意图确认" 只说以结构化文本展示，但没说这是什么 UI 形态。

**建议**：设计为 **确认卡片（Confirmation Card）**：
- 左侧：自然语言解析结果（"您要查看：2025年Q1各科室抗生素使用率环比"）
- 右侧：可展开的技术细节（指标、维度、时间范围、计算逻辑）——默认折叠，只有技术角色会展开
- 底部：两个按钮——「确认生成」+「修改条件」

#### 发现 3：导出性能预警（中等）

PRD 4.1 "一键导出 Excel/PDF/PNG"——大数据量场景下，浏览器直接渲染会导致卡死。

**建议**：
- Excel/PDF 导出：**后端异步生成** → 返回下载链接 → 前端轮询状态
- PNG 导出：前端 `html2canvas`（适合当前屏幕可见区），大表走后端 Puppeteer 截图
- Loading 状态：进度条而不是无限转圈

#### 发现 4：前后端数据协议建议补充（低）

建议 PRD 补充一份 **API 数据协议示例**——哪怕只是一个关键接口的请求/响应 JSON，开发理解成本会大幅降低。

### 🔍 莉卡（高级测试工程师）

> *"测试不是开发完才开始的事。PRD 阶段就要介入。"*

#### 发现 1：验收标准缺失（严重）

PRD 列出了功能，但没有定义 **验收标准**——什么情况下这个功能算"完成"？

**建议**：每个功能补充 Given-When-Then 验收条件。例如 AI 对话：
```
Given 用户输入"查看2025年Q1各科室抗生素使用率环比"
When AI 进行语义解析
Then 应在 3 秒内返回结构化确认信息
And 确认信息包含：指标名称、维度列表、时间范围、计算逻辑
And 用户可以点击"确认生成"或"修改条件"
```

#### 发现 2：边界测试场景缺失（严重）

PRD 没有定义异常场景的处理方式：

| 异常场景 | 预期行为（缺失） |
|----------|-----------------|
| AI 无法理解用户输入 | 提示什么？建议什么？ |
| 查询无数据 | 空状态展示什么？ |
| 导出超时（>30s） | 如何通知用户？ |
| 网络中断时 AI 对话 | 断线重连机制？ |
| 并发编辑同一报表 | 冲突处理？ |
| 权限变更（用户正在操作时被撤销权限） | 实时踢出 or 本次操作完成？ |

**建议**：补充「异常处理矩阵」——至少覆盖以上 6 个场景。

#### 发现 3：性能测试基线建议（中等）

PRD 4.1 只有单点指标，没有不同数据量级的性能预期：

| 数据量 | 下钻响应 | AI 解析 |
|--------|---------|---------|
| < 10 万行 | ≤ 1s | ≤ 2s |
| 10-100 万行 | ≤ 2s | ≤ 3s |
| > 100 万行 | ≤ 3s（预聚合） | ≤ 3s |

#### 发现 4：安全测试点补充（中等）

PRD 4.2 两条安全要求不够。补充：
- AI 对话输入框需做注入防护（Prompt Injection）
- 导出的 Excel/PDF 不应包含越权数据
- 审计日志不应记录患者明文数据

### 📐 艾塔（产品经理）——自我复盘

> *"作为作者，我用第一性原理追问三个根本问题。"*

#### 自检 1：用户角色模糊

PRD 把用户统称为"用户"，但实际上至少有三类：

| 角色 | 核心场景 | AI 对话方式 |
|------|----------|------------|
| 院领导 | 看趋势大屏，做决策 | "这个月抗生素情况怎么样"（模糊查询） |
| 科室主任 | 看本科室、对比同级 | "我科室 vs 全院平均"（对比查询） |
| 数据分析师 | 深度下钻、写报告 | "按科室统计 2025Q1 抗生素 MoM"（精确查询） |

**建议**：MVP 阶段优先服务「数据分析师」——他们容忍度高、反馈质量好、能帮产品快速迭代。

#### 自检 2：AI 对话可能过度设计了

用张小龙的克制哲学审视：80% 的高频查询可以预设（Top 20 报表模板），AI 对话只用于 20% 的长尾探索。

**建议**：标准报表目录预设高频报表，AI 对话定位为"标准报表覆盖不到的长尾需求"。这既降低 AI 调用成本，也减少用户学习负担。

#### 自检 3：MVP 需要大幅裁剪

**P0（第一版必做）**：
- AI 对话生成单表（不支持多表 JOIN）
- 报表预览 + 保存
- 基础权限（按院区隔离）
- 导出 Excel

**P1（第二版）**：下钻、同比环比、PDF/PNG 导出

**P2（第三版）**：目标值管理、科室共享、自定义仪表盘

## 四、P0 阻塞项

以下 4 项在进入开发前**必须**解决：

1. ⛔ **语义层架构方案**（意图 JSON vs 自由 SQL）——决定整个系统的安全模型
2. ⛔ **硬件最低配置 + POC 验证**——不验证就无法确认 3 秒 SLA 是否可达
3. ⛔ **数据模型 ER 图**——没有数据模型，开发和测试都无从下手
4. ⛔ **验收标准**——没有验收标准，开发不知道做到什么程度算"完成"
