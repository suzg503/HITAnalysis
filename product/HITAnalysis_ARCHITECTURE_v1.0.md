## 1. 架构概述

### 1.1 架构目标

| 目标 | 说明 | 优先级 |
|------|------|--------|
| **安全性** | 医疗数据不出院，AI模型本地化部署 | P0 |
| **准确性** | Text-to-Config确保计算逻辑准确 | P0 |
| **可控性** | 跨机构查询受权限强制约束 | P0 |
| **高性能** | AI解析P95 ≤ 3秒，查询P95 ≤ 2秒 | P1 |
| **可扩展** | 支持水平扩展，应对业务增长 | P1 |
| **可维护** | 模块化设计，降低运维复杂度 | P2 |

### 1.2 架构原则

| 原则 | 说明 |
|------|------|
| **安全第一** | 所有架构决策优先考虑安全性 |
| **简单优先** | 能简单不必复杂，复杂度要被管理 |
| **合适为宜** | 技术选型匹配业务阶段和团队能力 |
| **可演进性** | 架构为未来变化做准备 |
| **可观测性** | 系统状态透明，问题可定位 |

### 1.3 关键决策

| 决策ID | 决策内容 | 影响范围 | 理由 |
|--------|---------|---------|------|
| **D1** | 采用Text-to-Config，禁止AI直接生成SQL | AI架构、安全策略 | 确保计算逻辑准确，防止SQL注入 |
| **D2** | 智能洞察必须基于数据，展示数据来源和计算逻辑 | AI交互、内容安全 | 确保结论可追溯，提升可信度 |
| **D3** | 跨机构查询受权限强制约束，无权则AI拒绝执行 | 权限控制、AI交互 | 防止数据泄露，符合合规要求 |

    ↓

    ↓

    ↓

```

```
用户自然语言输入
    ↓

    ↓

    ↓

    ↓

    ↓
AI层：生成配置JSON（非SQL）
    ↓

    ↓
用户确认
    ↓
应用层：配置转SQL（基于预定义模板）
    ↓
数据层：执行ClickHouse查询
    ↓

    ↓

    ↓

### 5.2 数据权限设计

#### 权限范围定义

| 权限范围 | 说明 | SQL过滤条件 |
|---------|------|------------|
| **仅本人** | 仅本人创建的数据 | `WHERE creator_id = {user_id}` |
| **仅科室** | 所属科室的数据 | `WHERE dept_id IN (SELECT dept_id FROM user_dept WHERE user_id = {user_id})` |
| **仅院区** | 所属院区的数据 | `WHERE hospital_id IN (SELECT hospital_id FROM user_hospital WHERE user_id = {user_id})` |
| **跨院区** | 指定院区的数据 | `WHERE hospital_id IN ({authorized_hospital_ids})` |
| **全部** | 集团全部数据 | 无过滤条件 |

### 5.3 跨机构权限校验（D3决策）

#### 校验流程

```
用户发起查询
    ↓
提取用户权限（数据权限 + 菜单权限 + 按钮权限）
    ↓
检查查询是否涉及跨机构
    ↓
如果是跨机构 → 校验用户是否有跨机构权限
    ↓
无权限 → 拒绝并提示"您暂无跨机构查询权限，请联系管理员"
    ↓
有权限 → 在SQL中添加权限过滤条件（WHERE org_id IN (...)）
    ↓
执行查询
    ↓
返回结果
```

#### 核心设计点

| 设计点 | 说明 | 优势 |
|--------|------|------|
| **双重校验** | AI层和查询层双重权限校验 | 确保安全，防止绕过 |
| **显式授权** | 跨机构查询必须显式授权 | 防止数据泄露 |
| **自动过滤** | SQL自动注入权限过滤条件 | 确保数据安全 |
| **实时生效** | 权限变更实时生效（Redis缓存失效） | 提升用户体验 |
